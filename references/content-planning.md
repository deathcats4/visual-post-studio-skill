# Content Planning — 内容策划与来源管理

## 输入通路

- `scratch`：一句话主题或没有方向。首先构想2–5个角度（如收藏型清单、故事型介绍、比较型决策、实用操作），选择最能回答目标用户问题的一条。用户明确要求直接产出时自行选定合理方案。
- `adapt`：有文字、字幕、扫描件、截图。先获取全部相关素材；字幕可能有口误，操作文档通常更接近准确步骤，但如果出现冲突必须呈现差异、请求验证；绝不擅自发明技术事实。
- `reference`：参考图提供的是 **视觉设计依据**，不是关于新主题的事实依据；主题事实仍需单独筹备。
- `edit`：沿用已批准的 brief 和事实清单，只影响明确被修改的页面。

### 来源型教程先做全流程覆盖

当用户指定文档、视频字幕或截图时，先读完与任务有关的来源，再决定封面和页序。把目标任务从前置条件到操作、核对、常见失败和适用边界画成来源到页面的覆盖表；只纳入来源支持且与读者完成任务有关的部分。不能因为某一关键词显眼，就把整套内容缩成一个 API、功能或工具介绍。封面和页内标题以用户要教会的主题为准，不自动沿用项目名、账号名或相邻工具的宣传角度。

视频里的实操记录与文档中的推荐操作分开标明；如果两者不一致，呈现差异或请求核实，不拼成未经证明的步骤。真实 UI 是教学证据时，必须来自用户素材或可核实来源；无法取得时标记素材缺口，不生成看似真实的假界面。

## 逐条标记事实状态

| 状态 | 含义 | 处理 |
|---|---|---|
| SOURCE | 明确来自用户提供的源材料 | 保存文件名/章节/页码等出处 |
| VERIFIED | 经可信证据验证 | 标注验证方式和日期 |
| CREATIVE | 比喻、文案、主观意见或示例 | 可以创作，但不能伪装成真实统计或测试结果 |
| NEEDS_VERIFY | 无法确认的技术细节、数据、历史时效 | 审稿前提示，必要时删除具体断言 |
| NEEDS_ASSET | 依赖截图、真机、照片、证据图 | 使用占位计划；禁止假 UI、假证据 |

从零写科普、法规、医疗、金融、商品价格等信息时，不能为了完成图文而虚构可核查的事实；适当使用检索及权威资料。用户要求只用提供材料时，不通过外部消息偷偷补足关键缺口。

## “一篇内容只承诺一个价值”

用一句话写读者收益：“看完后，你会 ___”。随后建立 `claims.csv` 或 brief 里的事实表。

内容转图文 **不是** 把原文按字数切片；优先保留读者完成任务必需的事实、关键步骤和失败条件。把长原稿缩写成一句结论和可执行的图示；删掉口头开场、重复过渡和无关轶事。

推荐先写页标题和一行主要结论，再写每页必要的辅助信息。页面数量由复杂度与用户要求决定。

## 不得随意替换的事实

- 软件/产品名称、版本、菜单项、API调用顺序、文件名、路径、命令、提示词
- 数量、单位、比例、统计口径、日期
- 用户明确提供的第一人称经验和结论
- 依赖特定证据的前后对比

可用匿名假数据用于**示意图**，但必须清楚标识“示意”而不是“真实测试结果”。

## 内容节奏

避免每页铺满字。将背景介绍、why/how/when 分拆，内容简单时反而要减少页数。尽量不写重复的反面警告“这不是 X / 不是 Y”，除非这条限制确实影响读者完成任务或安全。
